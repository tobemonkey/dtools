# dtools 开发工作流

## 1. 核心原则

- 协议优先：先定义工具协议、API Contract、DTO、数据库字段，再实现
- 枚举统一：业务枚举必须包含稳定数字 `code` 和中文说明 `desc`，`code` 用于数据库存储和前后端交互
- 响应码统一：`ApiResponse.code` 必须是 `Integer`，并由统一响应码枚举维护，避免字符串 code 膨胀
- 主账本优先：MySQL 8 保存重要历史和配置，缓存与本地状态必须可重建
- Mock 闭环：真实数据库或系统不可用时，也能通过单元测试验证工具执行逻辑
- 原子实现：一个逻辑小任务独立完成，避免混入无关重构
- 小步提交：每完成一个可验证的拆分细节就提交一次，不等整个功能全部完成再提交
- 文档同步：复杂任务必须同时更新产品文档、技术文档和计划文档
- 用户确认优先：具体工具清单、视觉风格、桌面能力和非必要依赖必须先给候选方案，等用户确认后再实现

## 2. 阶段一：Init

动作：

1. 阅读 `AGENTS.md`
2. 阅读 `PLANS.md`
3. 阅读 `harness.yaml`
4. 阅读 `plans/<任务名>/task.md`
5. 判断任务类型：Core、Tool、Frontend、Desktop、Docs 或 Fix

输出：

- 当前任务类型
- 涉及模块
- 任务目录位置

## 2.1 阶段隔离总则

复杂工具 App 采用“阶段内共享上下文，阶段间强隔离”：

1. 产品探索阶段可以在单会话中完成，允许多角色共同讨论，目标是冻结 PRD、交互规则和 UI 图。
2. 架构设计阶段必须开启新会话或新工作上下文，只输入冻结 PRD、根规则和必要约束。
3. 编码实现阶段必须开启新会话或新工作上下文，只输入冻结 PRD、冻结架构、任务计划和必要规则。
4. 攻击测试 / QA 阶段必须开启新会话或新工作上下文，默认只输入代码、测试入口和运行方式，不输入产品探索和架构讨论过程。

每个阶段结束后，主 Agent 必须判断下一阶段是否应切换新会话。如果需要切换，必须提示用户：

- 当前阶段已冻结的产物
- 下一阶段目标
- 新会话需要携带的文件清单
- 不应携带的聊天过程或历史讨论

提示示例：

```text
当前产品探索阶段已完成，建议切换到新会话进入架构设计阶段。
新会话只携带：AGENTS.md、PLANS.md、harness.yaml、冻结版 PRD 和 UI 图。
不要携带：本阶段完整聊天记录、未写入 PRD 的口头假设。
```

## 3. 阶段二：Analyze

动作：

1. 梳理用户场景和边界
2. 列出需要用户确认的产品决策，例如工具清单、视觉风格、桌面能力范围
3. 定义 API Contract、工具协议和数据流
4. 设计 MySQL 8 主账本字段、索引和可回放信息
5. 说明使用的设计模式和原因
6. 更新 `analysis.md`

`analysis.md` 必须包含：

- 背景与需求
- 当前链路或初始链路
- 小功能点流程与数据流转
- 关键设计
- 使用的设计模式及理由
- 用户待确认决策
- Mock 验证方案
- 风险与待确认项

## 4. 阶段三：Design

动作：

1. 更新 `todo.md`
2. 拆分接口、实现、Mock、集成测试、文档归档
3. 明确每个子任务的产出物和验证方式
4. 明确每个子任务对应的提交边界，提交信息必须使用中文

## 5. 阶段四：Implement

每个子任务按以下节奏执行：

1. Sync：说明当前处理的子任务
2. Interface First：先写接口、DTO、Schema
3. Implementation：补实现逻辑
4. Mock Verify：运行 Mock 或最小测试
5. Todo Update：同步 `todo.md` 状态
6. Commit：只提交当前子任务相关文件，提交信息使用中文

提交拆分示例：

- `协议：新增 Jar 发布配置 DTO`
- `后端：实现 Jar 发布预览服务`
- `后端：补充 dry-run 执行步骤`
- `前端：新增 Jar 发布配置表单`
- `前端：展示 dry-run 结果和风险提示`
- `文档：记录阶段一发布边界`

禁止把协议、后端执行器、前端页面、文档和样式全部堆到一个“大功能完成”提交中。

## 6. 阶段五：QA

默认验证：

- `mvn -q -DskipTests compile`
- `mvn -q test`
- `npm --prefix frontend run typecheck`
- `npm --prefix frontend run build`

UI 交付：

- 新增页面或更新 UI 时，默认生成一张图片或截图作为展示说明，让用户直观看到效果；改动非常简单或用户明确不需要时可省略

阶段结束：

- QA 完成后必须输出攻击测试报告或验收报告。
- 如果后续进入修复阶段，默认开启新会话或新工作上下文，只携带 QA 报告、代码入口和必要规则。

## 7. 异常处理

- 发现工具硬编码无法复用：先抽象为工具协议或执行器
- 发现枚举缺少 `code` / `desc`，或接口直接使用 `enum.name()`：先修正协议规范，再继续实现
- 发现 `ApiResponse.code` 使用字符串或散落业务 code：先收敛到统一响应码枚举
- 发现未确认工具或样式已经被实现：停止继续扩展，先记录规范并等待用户确认是否保留
- 数据库不可用：保留 API 编译验证，记录 MySQL 联调风险
- 验证失败：记录失败命令、错误原因和下一步处理
