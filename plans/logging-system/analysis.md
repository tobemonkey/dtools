# 日志系统规范与请求详情日志分析

## 现状

- `TraceIdFilter` 已为每个请求生成或沿用 `X-Trace-Id`，并写回响应头。
- `GlobalExceptionHandler` 已按异常类型输出 `info / warn / error`。
- `AuthAuditServiceImpl` 已将登录审计写入数据库，并在审计失败时只记录警告日志。
- 当前日志主要集中在异常路径，正常请求路径缺少可观察信号。
- TraceID 尚未进入 SLF4J MDC，日志行无法天然携带 traceId。
- 项目尚未配置独立 `access.log`、`request-detail.log` 和日志保留策略。

## 设计判断

### 请求参数日志是否可行

请求参数日志有助于定位问题，但必须避免无差别明文记录。第一版采用独立文件、配置开关、异步处理、脱敏注解和长度截断，降低安全、性能和噪声风险。

### 为什么脱敏只走注解

运行时字段名兜底容易产生隐形规则：字段改名后可能失效，开发者也难以判断是否被脱敏。本项目第一版选择显式注解，字段是否脱敏、如何脱敏都由 DTO / Command / Query 上的注解决定。

### 为什么异步处理

请求详情日志是诊断能力，不属于业务主流程。主请求线程只采集轻量快照并投递队列；脱敏、序列化和写入在后台完成。队列满或日志处理失败时允许丢弃日志，不影响请求返回。

## 风险

- 如果 DTO 忘记添加脱敏注解，字段会按普通字段记录。
- 请求体需要通过 Spring 的缓存包装读取，避免影响 Controller 正常读取。
- 异步队列容量过小会导致请求详情日志丢弃，容量过大则占用内存。
- 本阶段只记录 JSON 请求体，文件上传和二进制请求只记录摘要或跳过 body。

## 后续扩展

- 增加慢请求详情日志。
- 增加按 URI 或 traceId 临时开启请求详情日志。
- 增加 ArchUnit 或单元测试扫描高风险字段名，作为构建期提醒。
- 将关键业务操作审计抽象为通用审计事件服务。
